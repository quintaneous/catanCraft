## Ordinary-server comparison

Use the same source, JARs, mod configuration, world state and host for each comparison. Record Java version/flags, hardware, free memory, swap/pagefile activity, storage, view/simulation distances, player count and whether the client shares the host. Start with the actual shipped settings. Mark the times of every action and save. Record cold startup through ready, allow five minutes of warm-up, and repeat each action window at least three times on matched disposable snapshots.

| Scenario | Measurements to compare |

## Capture and interpretation

- **Server ticks.** In the dedicated console use `perf start` around each event and retain the profiling ZIP under `debug/profiling`. Use the `ticktime` metric in nanoseconds divided by 1,000,000 for milliseconds per tick. Report sample count, median, p95, p99, maximum and counts above 50 and 100 ms. Normal 20 TPS allows 50 ms per tick. Short bursts need individual timestamps and repeated samples. Console lag warnings and a single average cannot supply percentiles.
- **CPU, allocations and GC.** Use a matching JDK 17 on the same host as the server, under the same account. Use `jcmd -l` to identify the dedicated server PID. Capture `jcmd <PID> VM.flags` and a bounded recording such as `jcmd <PID> JFR.start name=cityd settings=profile duration=120s filename=<absolute-path>.jfr`. Use `jfr summary <file>.jfr` and JDK Mission Control to align server-thread samples, GC pauses/after-GC occupancy, allocation samples and recorded file I/O with the action times. Pair a short profiled window with an unprofiled control. [JDK 17 diagnostic commands](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jcmd.html)
- **Heap and host RAM.** Sample `jstat -gc <PID> 5000` and process RSS every five seconds. Linux can use `ps -p <PID> -o pid,rss,%cpu` (RSS in KiB). On Windows record the server's Working Set and Private Bytes separately. Keep client and server PIDs on separate rows and capture total host available memory and paging. Compare heap used after comparable natural GCs, committed heap, RSS and host pressure together. The packaged Java runtime may need the matching JDK alongside it for diagnostic commands.
- **Client symptoms.** At the same timestamps record client FPS/frame time, client heap and connection latency. Recheck while stationary and during chunk travel. The dedicated profiling ZIP also contains per-level snapshots. Count rows in `chunks.csv` and `entities.csv`, excluding headers, and break down chunks by `full_status`, `ticking_ready`, `entity_ticking_ready` and `ticket`. Record the end time because these counts are snapshots.

Investigate construction validation, chunk loading, journal/region I/O, GC and the dashboard refresh only where recordings associate them with a repeatable symptom. Report the leading stack or event, the measured before/after effect on an identical workload, and the integrity checks for balances, tickets and restart recovery. Choose heap limits or code changes after that comparison.
